## Summary

`collectObjectNames` (`packages/core/src/slicers/prusaslicer.ts:28-53`) adds each object name twice, in two different forms, when PrusaSlicer labels objects in Klipper style or OctoPrint style. The `Set` then holds two names for one object. `validateGcode` (`packages/core/src/validation.ts:62-66`) counts `objectNames.length > 1` and raises the `multiple-objects` **error**, so the download is blocked for a correctly sliced single tower.

## Root cause

PrusaSlicer writes the same `label.name` into the G-code body and into `; objects_info = {...}` (source: `src/libslic3r/src/libslic3r/GCode/LabelObjects.cpp`, `all_objects_header_singleline_json` at ~line 208; `GCode.cpp:1499` writes `objects_info` unconditionally).

- **Klipper** (`LabelObjects.cpp:117-120, 198`): the name is sanitized (`.`, space, `-`, ... become `_`) and written as `EXCLUDE_OBJECT_DEFINE NAME='<name>' ...`. The regex `/NAME=(\S+)/` at `prusaslicer.ts:38` keeps the single quotes; `objects_info` has the name without quotes.
- **OctoPrint style** (`LabelObjects.cpp:107`): `label.name` is `<name> id:0 copy 0`. `PRINTING_OBJECT` (`prusaslicer.ts:9`) strips the ` id:0 copy 0` suffix from the comment; the `objects_info` name keeps it.

Firmware-style `M486 A<name>` (the only style in the fixtures) is unaffected because both sources agree. The existing Klipper test (`packages/core/src/recover-config.test.ts:28`) uses an unquoted `NAME=...stl_id_0_copy_0` and no `objects_info`, a format PrusaSlicer does not write, so it does not catch this.

## Reproduction

Klipper style, through `processGcode` with config PLA 230→220 step 5, h6, b1, M104:

```
; generated by PrusaSlicer 2.8.0
EXCLUDE_OBJECT_DEFINE NAME='temptower_v1_PLA_230to220_step5_h6_b1_m104_stl' CENTER=1,2 POLYGON=[[0,0],[1,1]]
M83
G1 Z0.20
G1 X20 Y10 E1
... (one layer every 0.2 mm up to Z 19.0)
; objects_info = {"objects":[{"name":"temptower_v1_PLA_230to220_step5_h6_b1_m104_stl","polygon":[[0,0],[1,1]]}]}
```

Observed `report.errors` (the only error):

```
multiple-objects: The file contains 2 objects ('temptower_v1_PLA_230to220_step5_h6_b1_m104_stl', temptower_v1_PLA_230to220_step5_h6_b1_m104_stl). Slice the tower alone.
```

OctoPrint style, through `inspectGcode`:

```
; generated by PrusaSlicer 2.9.0
; printing object temptower_v1_PLA_230to220_step5_h6_b1_m104.stl id:0 copy 0
G1 X1 E1
; objects_info = {"objects":[{"name":"temptower_v1_PLA_230to220_step5_h6_b1_m104.stl id:0 copy 0","polygon":[[0,0]]}]}
```

Observed `slicer.objectNames`:

```
['temptower_v1_PLA_230to220_step5_h6_b1_m104.stl', 'temptower_v1_PLA_230to220_step5_h6_b1_m104.stl id:0 copy 0']
```

## Impact

The UI states "Works with Marlin, Prusa and Klipper firmware" (`apps/web/src/main.ts:67`). Every PrusaSlicer slice for a Klipper printer profile with firmware-specific labels, and every slice with OctoPrint-style labels, is blocked by a false `multiple-objects` error.

## Suggested fix

Normalize names to one form before deduplication: strip the surrounding quotes from `NAME=`, and strip the ` id:<n> copy <n>` suffix from `objects_info` names the same way `PRINTING_OBJECT` does. Add fixtures with real PrusaSlicer Klipper-flavour and OctoPrint-style output, each including `objects_info`.
